# Threat model

Oak's security documentation covers the shared custody and authority model. The sections below add the LayerBank, Pendle, Borro and Chop boundaries and limits.
Use these sections when describing the impact of a report:

- **Custody:** [Where your key lives](docs/security.md#2-where-your-key-lives-local-self-custody): the wallet is created and used on the user's machine; the hosted service never receives it.
- **Authority:** [Keys and authority matrix](docs/security.md#4-keys-and-authority-matrix): what each key can and cannot do, including the single owner key and the sign-only price signer.
- **Burner bounds:** [Burner 90-day armed sweep rule](docs/security.md#5-burner-90-day-armed-sweep-rule) and [exact on-chain burner checks](docs/security.md#6-exact-on-chain-burner-checks).
- **Contract invariants:** [docs/INVARIANTS.md](docs/INVARIANTS.md), with Foundry tests in [contracts/test](contracts/test/).
- **Transaction checks and limits:** [Before anything signs](README.md#before-anything-signs) lists the local checks, the confirmation step and what they do not prove.

Report a vulnerability privately as described in [SECURITY.md](SECURITY.md).

## Ecosystem assets and trust boundaries

Oak connects to **34 ecosystem projects** on Robinhood Chain (`4663`). `earn_options` is a read-only comparison helper and is excluded from that count. The ecosystem modules other than ERC-8004 are mainnet-only.

| Asset | What is at stake |
| --- | --- |
| LayerBank USDG deposits (`lRobUSDG`), Pendle principal tokens (PT), ended-term payouts, Borro lending vault shares and Chop wrapped log / farm positions | Unauthorized signing, bad trade parameters, thin liquidity, third-party contract bugs or changes can cause loss or prevent an exit. |

LayerBank deposits and withdrawals call the pinned pool. Pendle trades call the pinned router. Borro deposits and withdrawals call the single Morpho Vault V2 contract verified on chain for that request (`0x0FBad98595b0186dA120E41f77C102beb49f803c` factory membership), with exact asset approvals to that single vault and never to `BorroBuilders` or an external router. Borro is an official Oak partner. Borro's own team runs its product and contracts; Oak didn't build them and doesn't run them. Chop log discovery, wraps, unwraps, 50/50 LP farming, unfarming and CHOP reward harvesting call the verified Chop log contract or pinned Chop contracts on chain 4663, with exact token approvals and a 1,000,000 gas floor on `chop_harvest`. Oak x Chop. Chop's own team runs its product and contracts; Oak didn't build them and doesn't run them. Oak pins addresses and function selectors, rather than contract code. Pendle's hosted API (`api-v2.pendle.finance`) supplies untrusted market lists and trade calldata and sees the requesting wallet address and trade amounts. Borro's web pages (`borro.markets/markets.json` and `contracts.json`) are optional, untrusted HTTP inputs queried by the Oak server for candidate discovery and labelled display rates; they are never used to construct calldata and are disabled during the strict local-guard rebuild. Separate add-on discovery and display requests still contact Borro from the computer, exposing its IP and User-Agent, without a wallet or amount. For an ended Pendle term, Oak builds the cash-out call locally from chain reads; an optional quote request to Pendle includes the wallet address and PT amount, lasts at most 1.5 seconds and can add a notice without changing the transaction. `earn_options` signs nothing. None of these four modules is registered on testnet.

## Threat H: Untrusted Pendle calls and limited LayerBank cash

- Oak decodes Pendle calldata using its own ABI fragments for exactly three functions: `swapExactTokenForPt`, `swapExactPtForToken` and `redeemPyToToken`. It refuses other selectors, a destination other than the pinned router, nonzero ETH value, a receiver other than your wallet, mismatched markets or tokens, external swap routers or swap data, and limit orders. Aggregator routing is off. Oak recomputes the minimum output from your slippage setting: defaults are 50 bps for USDG markets and 100 bps for stock-token markets, with caps of 100 and 200 bps. Quotes older than 30 seconds at signing are refused.
- Oak checks each market against Pendle's factory and checks the quoted amount against chain state. It refuses a trade if the chain read fails, the API amount differs too much from the chain estimate, or absolute price impact exceeds 3%. These checks bound the accepted call; they do not prove a fair market price. API free text is quoted as untrusted data. If the API is unavailable or fails validation, buys and sells are refused; no second calldata source is used.
- Ended terms use a locally built cash-out call, with minimum output 10 bps below the chain estimate by default and a 50 bps cap. The optional API comparison cannot change that call.
- LayerBank actions use only the pinned pool, and Pendle actions use only the pinned router. Approvals are for the exact amount of the action. LayerBank deposits check the reserve for pauses, freezes and supply-cap room. Withdrawals check cash on hand.

## Threat I: Unverified candidate vaults, governance drift and untrusted display data on Borro

- **On-request factory and anchor verification, with no HTTP in the local guard:** Oak keeps no fixed Borro vault allowlist and treats `borro.markets/contracts.json` as an untrusted candidate list. Every candidate vault is verified on chain at call time against Oak's trust anchors: the Morpho Vault V2 factory (`0x0FBad98595b0186dA120E41f77C102beb49f803c`, runtime code hash checked and `isVaultV2(vault) == true`), 18 share decimals, an underlying `asset()` matching `USDG` (`0x5fc5360D0400a0Fd4f2af552ADD042D716F1d168`) or an official stock token in Oak's local stock-token catalogue, and readable adapters. When the local guard rebuilds `borro_deposit` or `borro_withdraw` before signing, HTTP is disabled and the explicit vault address in the request is verified directly on chain.
- **Deposit gating on governance drift, while held-share exits remain open:** New deposits require the vault's live `owner()` and `curator()` to match Borro's anchored 2-of-3 group wallet (`0x8A22d6e75e9427b9D57e42a7984200029e7E173C`) and its adapter list to be readable; any mismatch refuses the deposit (`Borro's setup no longer matches what Oak checked. Nothing was signed.`). Withdrawals from a vault where the wallet holds shares are never blocked by governance, asset-rule, or adapter drift: Oak preserves the exit with a drift notice on the confirmation screen while still enforcing factory provenance, call target, asset decimals, and simulated receipt bounds (`floor(previewDeposit * 9950 / 10000)` on deposits; requested assets or `floor(previewRedeem * 9950 / 10000)` on `max` withdrawals).
- **Bounded optional HTTP display reads:** Rate figures from `borro.markets/markets.json` (`User-Agent: oak-core/borro`) are optional display metadata bounded to `0` through `1` (`0%` to `100%`), dropped when malformed or unavailable, and never used to build calldata or set transaction minimums. Free text from `borro.markets` is stripped and wrapped with `untrustedText`.

## Limits Oak cannot remove

- **Upgradeable contracts:** Pendle's router (`0x888888888889758F76e7103c6CbF23ABbF58F946`) is a proxy owned by a contract whose signers and threshold Oak has not verified. LayerBank's pool (`0x433e21dC2BF027910B1635653c2Eb630bC7dAD43`) and `lRobUSDG` are proxies too; Oak has not resolved the pool owner's or ACL admin's signers. Address and selector checks cannot verify new code behind an unchanged address.
- **Withdrawal cash:** LayerBank lends deposits out. Only the cash held by the pool at that moment is available for withdrawals. Oak refuses when no cash is available; if less than requested is available, it offers the smaller amount only if you agree. Oak cannot add cash, and LayerBank's own site has the same limit.
- **Early exits:** Selling Pendle PT before the end date uses the current market price and can pay less than you put in. Live terms are not promises from Oak.
- **Stock-token cash-outs:** An ended stock-token term pays the stock token itself, whose dollar value can change. It does not pay USDG. A swap to USDG is a separate step you confirm, and the issuer's transfer rules still apply.
- **Borro curator-controlled vaults, immediate reallocation, nested liquidity, token-issuer powers and unverified behaviour:** Each Borro vault is controlled by a 2-of-3 group wallet (`0x8A22d6e75e9427b9D57e42a7984200029e7E173C`) and has had no outside security check (Borro's registry states internal reviews only). While fee, gate and adapter changes carry a 3-day timelock, allocator changes and capital reallocation across markets act immediately, and underlying Morpho markets depend on price feeds and can accrue bad debt that vault share holders absorb. Withdrawals are limited to cash on hand: on stock-token vaults, cash on hand is the vault's idle balance plus free liquidity in its underlying Morpho market; on `bUSDG`, liquidity is nested across a multi-market Morpho adapter where most deposits are lent out and a liquidity adapter parked in the Steakhouse USDG vault, so only the unborrowed portion is ready to withdraw at once and withdrawals also depend on the parked vault's available liquidity until borrowers repay or the curator reallocates. `USDG` is an upgradeable Paxos token, and the official stock tokens lent in Borro's stock vaults are issuer-controlled beacon-proxy instruments whose role holders (often single wallets) can upgrade, pause or restrict transfers; lending a stock token also exposes the lender to changes in the stock token's dollar price. Oak checks factory provenance, runtime code hashes and role anchors on chain, not economic soundness or future curator actions; a contract that passes every on-chain check, or a curator reallocating into an illiquid or mispriced market after a deposit, can still lose funds.

## Before a deposit or term

Read the confirmation screen's end date, early-exit line, risk line and cash-on-hand line. Choose an amount that allows for a partial withdrawal or a sale at the current market price. Expect the stock token itself when withdrawing from a stock-token vault or cashing out an ended stock-token term.


### Threat K: Gloam notes, proofs and relay

Gloam is an official Oak partner. Gloam's own team runs its product and contracts; Oak didn't build them and doesn't run them.

- The encrypted local note store and receive key are spend authority. Theft can expose funds; losing both the store and backups loses them. New change and sweep notes require new backups. Never paste notes, bearer packages or backups into an agent. Claim accepts sealed tickets to the receive tag and sweeps ready payments immediately; the payer can take a payment back before it is claimed.
- Only shield deposits sign wallet transactions. Exact USDG approval and `shieldBound` target the pinned pool through Oak's preview, local guard, human confirmation in chat and sender. Pay, claim and whole-note cash-out are proof-authorized relay submissions, with human confirmation in chat bound to the payload hash. Cash-out is only to this wallet and publicly reveals its receipt amount.
- The session-free Oak forward sees the IP and public proof; a cash-out also names the wallet. Deposit attribution carries a public shield hash linkable to the wallet. Oak logs none of those fields; memory rate limits do not prevent all key-quota abuse. The unauthenticated forward can consume Oak's service-key allowance. Relay availability and future billing remain third-party/operator risks.
- Public relay fallback occurs only on unreachable/5xx errors, reports that Gloam saw the computer's IP and loses attribution; a 4xx never falls back. A definite relay 4xx refusal fails that plan's fresh reserved notes that have no `txHash` while keeping the input note unspent, and claim summaries show the allow-listed SDK sweep reason or HTTP status. Private actions never self-broadcast. Circuit downloads expose the computer's IP to Gloam; SHA-256 pin checks refuse altered files.
- Gloam is in Mainnet Beta. A single EOA owner can lower deposit limits or fees immediately; raising the fee (up to 1%) or limits requires a three-day public wait. USDG's issuer can freeze the vault's tokens. Contract or circuit faults can lose money; no claim extends an outside contract review to the circuits, relay or SDK.
- The fresh SDK has no established provenance. The optional `@oakagentkit/gloam` package has its own dependency and license supply chain; its absence or API mismatch refuses with an install command. Oak does not import its SDK at startup. Notes and proving stay local; the hosted module refuses all Gloam tools and `positions` cannot inspect private notes.


### Threat J: Chop contracts and exit limits

Oak x Chop. Chop's own team runs its product and contracts; Oak didn't build them and doesn't run them.

Chop's upgrade key can replace log, staking and rewards implementations without a timelock. Oak rechecks the registry, proxy runtimes and beacon anchors for every action; implementation drift refuses wraps and farms, while verified exits carry a changed-code warning. The underlying unwrap has no on-chain minimum, so a fresh locally read floor and human confirmation cannot guarantee the eventual payout. A reward payout failure may be caught by Chop while the transaction succeeds; Oak checks received CHOP separately and applies a 1,000,000 gas floor. Wrapping or farming OAK moves OAK from the wallet into the Chop log or farm contract. Logs are permissionless: registry verification is not a safety verdict. Oak refuses the dormant colliding OAK token. No contract audit claim is made.

### Threat L: Factor desk contracts, engine and advance limits

Factor is an official Oak partner. Factor's own team runs its product and contracts; Oak didn't build them and doesn't run them.

- Factor's desk contract on Robinhood Chain (`FactorDesk` `0x487Eb282E9Aa56aE871c15A16C5B061b9d2faA6F`) has no owner or pause role and enforces fixed immutable rules, but Factor's off-chain engine and API (`factoragents.fun/api/v1`) can lag the chain by up to two minutes. Oak pins the six deployed Factor contracts (`FactorDesk`, `FactorPool`, `FactorLine`, Factor's burn pot contract, and two deployment contracts) by address and runtime `keccak256` code hash, checks `burnPot()` and `gateway()` immutables on every write, and re-reads `job(uint256)` on chain; API records are labelled display data and never authorize an action.
- Factor's `/state` endpoint is cross-checked against the pinned desk before any write or signature; a desk mismatch refuses all operations, and `asOf` must be within ±120 seconds of the local clock. If `/state` is unavailable, chain writes (`register`, `draw`, `deliver`, `decline`) can proceed using the pinned code hash, but message signatures refuse because they require `asOf` to date the message.
- Wallets with contract code (including EIP-7702 delegations) are refused for Factor writes and signatures, because the desk holds contract payouts as `owed` and Oak has no `collect` or `collectTo` tool yet. Credit-line jobs (`FactorLine.keyOf` non-zero), gasless relayer execution, `from: 'compute'` advances (which send ETH to Factor's gateway as off-chain credit), and offers jobs (`needs_offer`) are also refused.
- Gateway (`0xe4314Ba4DAe5f31582ec23812d5f40287f1eFdE0`) and deployer admin (`0xafA96B2F796968dA543B77E9d1a04f80321acD04`) addresses are plain accounts with no contract code; who holds their keys is not shown on chain.
- If a job with a drawn advance is not delivered within 12 hours after its due time (`dueAt + 12h`), anyone can trigger `refund(id)` on chain and that wallet is permanently barred from drawing from Factor's pool. Declining a job is possible only before drawing on it; a rejected job settles at half payout with no appeal.
- Signed pay links cannot be revoked once created and can be paid by anyone holding them until expiration (capped at 1 to 30 days). Agent names are first come (`register` can run once per wallet), and fixed-price open-job applications cannot be withdrawn. Engine signature templates enforce strict pre-sign text rules (NFC-normalised length limits, no links or domain names, no control or bidi characters).
- By default (`show: false`), work text stays on this computer and the add-on hashes `work` locally so only its `keccak256` proof goes on chain. If public display is explicitly chosen (`show: true`), the work text passes through Oak's server to Factor's engine after on-chain delivery and becomes public and permanent on Factor's job page with no edit path.
- Factor's spec pack documents commit `713df4e`, whereas Oak binds to the deployed desk runtime code hash and verified constants on Robinhood Chain.

### Threat M: Raeto off-chain credit, API keys and spending limits

The owner-only payment journal retains an approved payment signature only while its authorization is unresolved. An explicit retry checks chain evidence and reuses the same authorization and nonce, with no new payment signature. A reader who steals this journal can submit that already-approved payment to the pinned Raeto payee while it remains valid. Terminal settlement removes the signature; authorization history remains local.

Oak integrates with Raeto. Raeto's own team runs its product and contracts; Oak didn't build them and doesn't run them.

- Raeto credit is held off chain on Raeto's servers for spending only, not in the wallet, and cannot be converted back into USDG. If Raeto is unavailable or stops working, unused credit cannot be recovered. The API key is stored locally in `~/.oak/raeto.json` (mode `0600`, written atomically under lock and removable via terminal-only `oak raeto forget`) and never sent to Oak's hosted service; if stolen from this computer, an attacker could spend Raeto credit (`limitUsd` is set to the balance on each sign-in and top-up). Raeto refuses new calls once the balance or key limit is used up, but calls are charged after completion, so the last call can cost a little more than what was left. The key cannot withdraw funds, manage keys, or sign into Raeto's console.
- Raeto's EIP-191 sign-in challenge contains no domain, chain ID, or expiration line inside the signed text. Oak bounds replay risk by validating the challenge against a byte-exact pinned template, checking that the wallet matches and the nonce is a 32-hex string, enforcing Raeto's 10-minute `expiresAt` locally before signing, sending only over HTTPS to pinned `api.raeto.cc`, and receiving a key that cannot withdraw funds.
- When topping up with USDG ($1 to $50) via EIP-3009 `TransferWithAuthorization` (submitted by Raeto's facilitator `facilitator.priors.trade`, which Oak never contacts directly), a consumed nonce (`authorizationState` true) is not proof of payment: it may reflect a `cancelAuthorization` executed outside Oak. Oak treats a top-up as paid only when USDG logs show both `AuthorizationUsed` and a matching `Transfer` to Raeto's pinned `payTo` address (`0xf0cc2fe5a90a3bb784de818f6e2061fd99c236bf`) in the same transaction, reports `AuthorizationCanceled` as cancelled, never retries the paid GET implicitly, and pauses for operator recovery when a reply is lost after on-chain settlement.
- Oak enforces local per-call (default $0.50, ceiling $5.00) and UTC daily (default $2.00, ceiling $25.00) limits in `~/.oak/raeto-ledger.jsonl` against Oak's upper-bound cost estimates before dispatching paid calls. If a request times out, errors without request-level cost evidence, or receives an unconfirmed response, its reservation stays `uncertain` at the full upper-bound amount against that UTC day's limit. Uncertain reservations are never settled or released from an account balance check.
- Prompts, search queries, and fetched URLs are sent directly from this computer to `api.raeto.cc`, and model prompts are forwarded to third-party model labs; Oak's server sees none of them, and Oak stores no prompts, queries, or replies in local ledgers or logs. Bare-key redaction strips `sk-raeto-` strings across outputs, errors, logs, and the ledger, and a secret-paste guard refuses inputs containing `sk-raeto` or a raw 64-hex private key. Model answers, search snippets, and fetched pages are third-party text that could attempt prompt injection; Oak wraps them with `untrustedText` and `raeto_read_page` refuses non-HTTPS, localhost, link-local, and private IP addresses.
- Pairing an ERC-8004 identity with a Raeto account publishes a weekly statement of what the agent spent and received on Robinhood Chain. These records are public and permanent and cannot be taken down (record pairing ships switched off until Raeto's pairing approval template is pinned). Record pairing gives a free opening statement, then costs 0.05 USD per active week from the agent's balance, which can move the Raeto balance outside any Oak call and is flagged during `raeto_status` balance checks.

### Threat N: Multi-step plan approval (`oak_plan_run`) and skim risk

- **Skim risk on multi-step approval:** One human decision in `oak_plan_run` covers 1 to 8 listed transactions across 1 to 8 steps on Robinhood Chain (`4663`), so a person who skims a multi-step summary in chat could approve a batch without reading every line. Oak mitigates this by putting Oak's own decoded summary line first, followed by per-token spend totals, total maximum network fee, and every transaction's decision line, exact permissions, and pinned module contract in execution order.
- **Hard scope and exclusions:** Plans are capped at 8 steps and 8 transactions on chain `4663` only. Oak refuses plan approval for third-party recipients (`send`), message or typed-data signatures, Gloam relay actions, NetNet card plans, identity registration or tags, token launches, HoodLock, Factor, Raeto, Priors, `relay_bridge_out`, local-screen tools, and any step whose calldata depends on an earlier step's mined ID or hash. The agent never shrinks or raises simulation caps itself; caps come from simulation and the person decides in chat.
- **Digest-bound per-step consent and live re-checks before each signature:** Consent is seeded per step index and bound to the `keccak256` digest of the prepared plan (`PreparedPlan`), running under one wallet lock and recording one receipt row per listed step in `~/.oak/approval-receipts.jsonl`. Immediately before each signature, Oak re-simulates against current chain state and re-checks the local guard, exact approvals, outflows, authority, and confirmed bytes. An unlisted step never signs under a plan approval. If a step's simulated terms worsen (higher spend, lower output, a new approval, or gas above `1.2x` the planned step cap), Oak re-asks once in chat showing the change; a second change or any step failure stops the plan immediately with nothing after it signed, while leftover permission cleanup still asks in a separate confirmation.


## Privacy boundaries and retention

Local signing keeps the wallet key on the computer. Other data can leave: hosted tool calls include the wallet session, partner APIs receive their documented request fields, and RPC providers see the IP, wallet queries, calldata and signed broadcasts. The default mainnet RPC is `https://rpc.mainnet.chain.robinhood.com`; approval history uses wallet-filtered logs and execution checks can use transaction traces. Hosted Meridian perps reads pass through Oak, while direct perps actions contact Meridian from the computer. The privacy page lists partner hosts and wallet-bearing calls.

Hosted Agent Wormhole checks send selected token name, symbol and description text through Oak by default. Set `OAK_WORMHOLE_PAYER_MODE=off` to keep only offline checks and free snapshots. Orbio conversations go to `api.orbio.so`. Raeto sees the computer's IP and wallet-bound key usage, and can link prompts to the wallet; model prompts also reach the model lab. Factor signature preparation fetches `/state` directly; public work text passes through Oak to Factor after delivery, while default private work stays local.

Receipt exports enter the chat with the full history or accounting CSV. Approval previews also reach the MCP host as redacted log notifications containing full calldata. The host and model provider may retain these. Receipt-verification success summaries can still expose provider error text, including keyed RPC URLs, and some local filesystem errors can expose OS paths; these paths require further fixes.

`oak_portfolio` also sends your holdings, positions, and rewards view into the chat (for an offline accounting CSV that stays out of chat, run `oak receipts export accounting-csv` in your own terminal). `oak_whois`, `oak_doctor`, and `oak_dry_run` read through the configured RPC (seeing the queried address, trace probes, and simulated calls; `oak_doctor` also checks ETH and USDG prices, stock USD estimates, and hosted `account` status), while the Merkl card reader uses Oak's hosted `merkl_campaigns` read with the pool's campaign query and not the wallet.

The approval archive keeps only public revoke metadata, with legacy signed rows migrated under the wallet lock on archive access. Signed fee versions remain only in pending recovery state. Gloam acknowledgement names use a note-secret HMAC; legacy wallet/hash names migrate on a Gloam request with the original encrypted notes. Marker counts and timestamps remain visible. Circuit cache entries use owner-only file and link checks.

Local history, received-token hints, cleared records, historical approval receipts, replaced encrypted wallets and old unlock keys are not automatically pruned. Signature records prune only on later signing reconciliation. Config can contain plaintext keyed RPC URLs. Launch/private-test logs contain event and tool only. Each backup run removes its own plaintext staging bundle on normal exit; forced kills and older bundles need operator cleanup. Encrypted remote snapshots can outlive live-store expiry. Live host configuration and partner retention were not inspected. ERC-8004 profiles and metadata are public and permanent; free-text fields can contain personal information or pasted credentials that field-name checks cannot recognize.
